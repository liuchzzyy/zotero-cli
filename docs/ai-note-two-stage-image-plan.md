# ai-note 两阶段图文分析与发送前图片压缩方案（待审查）

状态：**用户已批准实施；实现及验证记录另见工作区和测试报告**。本文件记录建议与验收标准，不代表模型或网关的真实限制已经核实。

## 目标与边界

- 保留完整的正文与 SI 结构化文字、表格、图注和来源信息；在最终分析中使**全部有效正文图片**确实被视觉模型看到，SI 图片在安全预算和可读性条件下尽量多送入。任何一张正文图片无法合规发送时，在写入 Zotero 前报错，不能将仅有图注的描述标成视觉观察。
- 将笔记分析固定为**文字取证、视觉成稿两个阶段**：一次从文字提取结构化证据，一次结合该证据和图片生成最终笔记。这里的“两次”指两次主分析请求；现有非 dry-run 分类调用、可选 short-note 调用以及失败后的格式/内容重试仍可能增加实际 API 请求次数。只在最终结果通过验证后写入 Zotero。图片确实超出一次视觉调用的能力时，两阶段流程无法保证目标：明确失败；是否增加额外视觉批次作为后续独立决策，不默认偷偷执行。
- 保持代码预检：单张**待发送图片**至多 5 MiB，请求体至多 20 MiB；同时满足路由上下文预算、输出预留和安全余量。两数是项目自己的预检阈值，不声称为 API 官方上限。`REQUEST_CEILING=800_000` 是当前基于字符与每图 4096 单位的近似估算，不能当作真实 token 数。
- 不修改 Zotero 原始 PDF、MinerU 原图和现有缓存；仅在内存或受控临时空间生成此次请求的衍生图片。不得在保证质量之前把 5 MiB 限制改大，也不得对超限图直接截取文件字节。

## 实施前基线依据

- `src/zotero_cli/ai_notes/evidence.py`：`MAX_SI_IMAGES=30`；按文字长度和每图估算先选图，构造 base64 载荷之后才检查 20 MiB 请求体。`plan_with_coverage` 将未发送图号追加到 prompt 并再次规划。
- `src/zotero_cli/ai_notes/analysis.py`：一次生成请求带完整文字与选出的图片；`--dry-run` 报告主图/SI 图计数、请求体估算和预算路由。
- `src/zotero_cli/ai_notes/access/client.py`：图像能力拒绝可退化为纯文本重试；两阶段方案下，最终请求若要求全部正文图，此退化不能再算为成功。
- 当前仓库无直接图片编码依赖（`pyproject.toml`）；实现时应评估引入 Pillow 的维护成本与解码安全，使用 `uv` 管理依赖。这是实施前状态；实施已通过 uv 引入 Pillow，真实试验结果见 `ai-note-two-stage-verification.md`。

## 处理流程

1. **解析与归属检查**：沿用 PDF 去重、main/SI 分类和图号、页码、附件来源。确认每张正文图文件可用且是支持的格式；解码时设置像素数量上界并拒绝损坏图、异常长宽比/尺寸和文件类型伪装。分类错误导致正文图被当成 SI 的风险，应纳入样本核查。
2. **第一次调用：文字证据**。发送完整结构化文本、表格、图注与现有论文类型模板所需的元数据，不附任何图像；返回有固定结构、长度上限的证据包：关键主张、数值及单位、实验条件、附件/页码/图表编号、待图片核对的问题。逐条标记 `text_only`，不得形成“见图中曲线”一类视觉结论。证据包不写入 Zotero；若解析失败、丢失必需来源或超出第二次预算，整次任务失败，不静默压缩/删减证据。
3. **只在发送前压缩图片**：原图已符合限制且预算足够时优先原样发送；否则针对每图生成编码候选并测量**实际编码大小**。优先去除无用元数据、所有图先尝试无损 PNG 重编码，保留解码像素与尺寸；不降低 JPEG 质量、不缩小图片。这样无需用图像类别猜测是否可以牺牲细节。不能仅凭源文件大小判定质量或预估压缩比。保留图号到原路径、候选编码参数、像素尺寸和摘要哈希的映射，以便复查；不持久保存原图副本。最低分辨率/质量参数和具体 codec 在小样本视觉检查后确定，而不是在计划中臆定。
4. **第二次调用：视觉核查并成稿**。携带第一阶段证据包、简短核查指令、全部可发送的正文图和预算内尽量多的 SI 图；保留图号、附件和页码映射。核查中间包和图片是否一致后生成现有 `sections` 格式笔记；无图的 SI 仅可引用文字/图注。若压缩后正文图仍超过单图、请求体或上下文预算，或模型拒绝图片输入，失败并告知哪个图/哪个预算构成阻碍，不改为纯文本完成写入。
5. **SI 选择**：取消固定 30 张阈值；先保留正文引用过的 SI 图，再让其余图覆盖不同章节/页码。选择过程同时检查上下文预估和**最终序列化 HTTP 请求体字节数**（含 JSON、base64、消息结构与重试附加文字），不只按图片张数。容量不足时仅移除 SI 图片，并在最终输入与 `--dry-run` 中标记每张未发送图片及原因；必要时重新测算说明文字占用的预算。对于损坏或小于最小可读阈值的正文占位图，需预先明确是无效块还是必需图，不以静默跳过代替决策。
6. **重试、失败及写入**：两阶段每次调用分别预检；格式/内容重试重新核算文字、图片和请求字节，保留同一组正文图。`finish_reason=length`、第二阶段缺失正文视觉输入、无法解析或内容不可渲染均不得写笔记。沿用现有幂等预留和远端写入结果处理；两阶段之间不新增 Zotero 写入。

## 图像质量与科学性门槛

- 图像压缩是有损变换的可能来源，字节达标不代表信息等价。对实际候选验证坐标刻度、图例、面板字母、比例尺、显微形貌、弱峰/细线、误差棒以及颜色含义；不合格的候选不能发送并假称原图已送达。
- 自动门槛只能查尺寸、格式、解码与清晰度的部分代理指标；“图内科学信息未损失”须对代表性图组做人眼抽检，必要时用视觉模型对原图/压缩图作盲比，但不得以模型自评替代人工判断。
- 中间证据包须保留数值的测试条件与出处；第二阶段不能仅靠摘要重建表格或机制链。图像越多还可能降低模型注意力和生成完整度，因此以笔记质量比较决定最大可用量，而非只追求发送张数。

## 分步实现与验证（得到用户确认后）

1. **固定基线与样本**：以当前 `ed5cba7` 工作树为基线，不覆盖已有修复；选正常论文、多图综述、正文图很多/SI 图很多、线图与显微图混合、包含极细标签的样本。记录现有 `--dry-run` 覆盖计数、请求预算、耗时和用量；如需真实模型试验，先确认测试的本地/远端环境及成本。
2. **先做图片管线的失败测试**：断言原图不变；超限图片在可读压缩成功时可用，不可读/损坏时明确失败；base64 与最终请求体字节数精确计量；正文图始终全部保留，SI 由可用预算确定，优先引用并兼顾分布；极限预算不发生不终止的重新规划。
3. **实现图片候选生成与双预算规划**：在 `ai_notes` 职责范围内封装解码/编码与预算器，去除 `MAX_SI_IMAGES` 常量及与 30 张绑定的断言。以可复用的单张衍生数据供最终请求发送，避免重复解码与无界内存占用。
4. **先做两阶段工作流测试**：第一次请求无图且输出有来源的证据包；第二次请求含证据包和全部正文图；视觉能力拒绝、超限、截断或中间包无效时无 Zotero 写入；格式/稀疏重试仍按阶段重新预检；`--dry-run` 清楚分别展示两阶段估算与覆盖。
5. **实现编排并更新文档**：调整 `analysis.py`、`generation.py`、模型客户端及模板/输出契约；更新 README、`skill/zotero-cli/references/ai-note-verification.md` 中仍写“30 张/500k”的旧说明。若新增依赖，更新 `pyproject.toml`/`uv.lock`；避免改变无关命令。
6. **离线门禁与受控质量试验**：运行针对性测试和 `uv run ruff check .`、`uv run ruff format --check .`、`uv run ty check`、`uv run pytest -q`、`uv build`、`uv run zot ai-note --help`。随后在用户确认的模型环境中比较同一批条目：正文图送达率须为 100% 或明确失败；SI 送达数及遗漏原因可审计；必需章节/表格完整率、数值与图号准确率、无依据视觉断言率不得比现行方案恶化；记录真实 token、截断、耗时与费用。未观察到质量对照结果前只报告覆盖改进，不能宣称“质量无损”。

## 风险、备选与待审查问题

- **能力上界**：压缩只减少请求字节数，通常不能按比例减少模型对每张图的 token/处理开销；若全部正文图的预算超过一次视觉调用，固定两次不可行。备选是增加有界的视觉批次，最后再做一次有来源的综合；此项需单独确认调用次数、成本及证据合并规则。
- **信息损失**：科学线图的刻度/图例可能先于尺寸门槛失真。无法取得可读候选时宁可失败；不要用“压得更狠”掩盖问题。
- **证据转述**：第一次文字证据包可能漏掉后续看图所需的条件；过于短的摘要会让图文错配。保留引用和条件并用样本做逐条核对。
- **接口容量**：5 MiB/20 MiB 仅是代码防线；实际 Magpie/模型的图片数量、分辨率、请求体及 token 上限尚未核实。真实试验若出现更严格的服务端限制，回到计划修订，不以超限重试作为隐式降级。
- **待用户决定**：当一次视觉调用装不下全部正文图时，是保持“固定两次且失败”，还是允许增加额外视觉批次？建议先实现明确失败，并在代表性数据上量化这一场景出现频率后再决定。

## Review Focus

1. **多图且压缩后超过 20 MiB**：必须在发送前失败或只移除 SI；由步骤 2–3 的序列化体积测试覆盖。
2. **正文图超限或压缩后细节不可读**：不得以“发送成功”代替完整视觉证据；由步骤 2 的无损原图/编码边界测试及步骤 6 的人工抽检覆盖。
3. **正文图单独超出上下文预算**：必须在写入前失败，并列明原因；由步骤 4 的两阶段失败测试覆盖。
4. **图像能力拒绝后的纯文本降级**：不得将纯文字结果写成看过全部正文图；由步骤 4 的模型拒绝测试覆盖。
5. **首次输出缺少原文实验条件或来源**：禁止据此生成最终笔记；由步骤 4 的中间包校验测试与步骤 6 的样本对照覆盖。
